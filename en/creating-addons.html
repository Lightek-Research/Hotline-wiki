Creating addons

Download all three tutorial files. The archive lists installation paths; the test Script is disabled.

This tutorial builds a small server system with an enabled/disabled state, connects it to HOTLINE and records its commands. It is a teaching example: a real integration uses your camera, pyrotechnics, screen or other system's actual API.

Install HOTLINE 0.14.0 and verify normal GLights recording first. For ready-made integrations, see Addons.

How the connection works

The external system reports a change → Connect forwards a command through emit → HOTLINE stores it in a cue. During playback, HOTLINE checks arguments through Validate and calls Run. Reset handles resetting state.

The addon does not replace your system's API or implement a new timeline. It declares a fixed command set and connects notifications about actions.

Step 1. A teaching system

Create a ModuleScript named ExampleSystem directly in ServerScriptService:

local changed = Instance.new("BindableEvent")
changed.Name = "Changed"
changed.Parent = script

local enabled = false
local System = {Changed = changed.Event}

function System:SetEnabled(value)
    assert(type(value) == "boolean", "Expected boolean")
    if enabled == value then return end
    enabled = value
    print("ExampleSystem enabled:", enabled)
    changed:Fire(enabled)
end

function System:GetEnabled()
    return enabled
end

return System

This system only prints state to Output. In a real product, SetEnabled controls a device and Changed reports the change. This teaching API uses colon calls.

Step 2. The complete addon

Create a ModuleScript named Example inside ServerScriptService.Hotline.Addons and paste the full code:

local Addon = {
    Id = "Example",
    Version = 1,
    Enabled = true,
    Commands = {},
}

Addon.Commands.SetEnabled = {
    ReplayOnSeek = true,
    Validate = function(args)
        assert(args.n == 1 and type(args[1]) == "boolean",
            "Example.SetEnabled expects one boolean")
    end,
    Run = function(api, value)
        api:SetEnabled(value)
    end,
}

function Addon.Resolve(context)
    return context.RequireApi("ServerScriptService.ExampleSystem")
end

function Addon.Connect(api, emit)
    assert(api.Changed and type(api.SetEnabled) == "function",
        "ExampleSystem API is incompatible")
    return {
        api.Changed:Connect(function(value)
            emit("SetEnabled", value)
        end),
    }
end

function Addon.Reset(api)
    api:SetEnabled(false)
end

function Addon.Snapshot(api, emit)
    emit("SetEnabled", api:GetEnabled())
end

return Addon

The event target is @Example. The SetEnabled string in emit must match the Commands key exactly. Id determines the target and settings key; the ModuleScript name determines its GetAddons row. They match here to keep the example clear.

Step 3. A test sequence

Create an ordinary Script ExampleTest in ServerStorage and disable it with Enabled=false:

local Api = require(game.ServerScriptService.Hotline.Scripts.Api)
assert(Api.WaitForReady(20), "HOTLINE is not ready")

local deadline = os.clock() + 15
while true do
    local addons, err = Api.GetAddons()
    assert(addons, err)
    local status = addons.Example
    if status and status.state == "ready" then break end
    if status and status.state ~= "loading" then
        error("Example addon: " .. status.state .. " / " .. tostring(status.error))
    end
    assert(os.clock() < deadline, "Example addon is not ready")
    task.wait(0.1)
end

local System = require(game.ServerScriptService.ExampleSystem)
System:SetEnabled(true)
task.wait(2)
System:SetEnabled(false)

Restart Play after adding the modules. Create/select a cue in HOTLINE, choose Timed and press Record. From SERVER Command Bar, launch a test copy:

local test = game.ServerStorage.ExampleTest:Clone()
test.Enabled = false
test.Parent = game.ServerScriptService
test.Enabled = true

After two seconds, press Pause in HOTLINE. Events should contain two @Example / SetEnabled commands: true and false approximately two seconds apart. Save and replay the show; Output should repeat the changes. Reset can print additional disabled-state messages because it also controls the system.

For Capture, reset the system to false, start Capture recording and execute the enable action. The first command is stored at offset zero; the second action occurs after that recording has already finished.

Step 4. Initial state and options

To record current state at the start of Timed, merge this into the existing Config table:

AddonOptions = {
    Example = {
        SnapshotOnRecord = true,
    },
},

Snapshot does not enable the system: it emits the current value. HOTLINE calls it only for Timed with SnapshotOnRecord enabled. Capture never takes an automatic snapshot. If AddonOptions exists, add Example inside it.

To make the path configurable, replace Resolve with:

function Addon.Resolve(context)
    return context.RequireApi(context.Options.ApiPath
        or "ServerScriptService.ExampleSystem")
end

Module contract

PartPurpose
IdUnique identifier, up to 50 characters: a letter first, then Latin letters, digits, _ or -.
EnabledFalse disables the module after restart.
CommandsNon-empty fixed command table. Every command requires Validate and Run.
Resolve(context)Returns the external API or nil if the dependency is absent.
Connect(api, emit, context)Optional capture setup; returns an array of connections supporting Disconnect.
Reset(api)Optional safe state reset/disable action.
Snapshot(api, emit)Optional initial-state capture before Timed.
ReplayOnSeekTrue permits this command during seek restoration; default false.

An addon without capture setup can still support manually authored Events. If recording is required, HOTLINE needs emit to learn about actions.

context.Config is HOTLINE Config. context.Options is Config.AddonOptions[Id] or an empty table. context.Root is the Hotline folder. context.Resolve(path) finds an Instance; context.RequireApi(path) requires the ModuleScript or returns nil if absent.

Supported roots: Workspace/workspace, ServerScriptService, ServerStorage, ReplicatedStorage. Paths split on dots: for object names containing a dot, write your own Resolve using direct FindFirstChild. Spaces and parentheses work if names have no dots.

Arguments and validation

Pass normal Lua/Roblox values to emit, not JSON or pre-encoded tags:

emit("SetEnabled", true)
-- A two-argument command could use:
-- emit("SetColor", "Front", Color3.fromRGB(255, 0, 0))

The SetColor comment only illustrates the format. Add that command to Commands before using it.

Validate receives unpacked arguments. args.n preserves the original count, including nil. Reject with assert/error: returning false alone does not reject a command. Run receives the API followed by ordinary parameters.

Validate arity, types, allowed effect names and actual system ranges. Exclude NaN/infinity for numbers. Check referenced objects belong to the intended system. Never select an arbitrary API method from a user-provided string.

Up to 12 arguments are supported: nil, booleans, finite numbers, strings, bounded tables and supported Color3/Vector3/ColorSequence values. Shared codec/PayloadGuard limits apply; decoded strings are limited to 4000 bytes. Arbitrary Instances are not supported: the current reference decoder permits Workspace BasePart targets. Stored arguments use HOTLINE's shared serializer.

APIs without change signals

A dedicated successful-command signal is preferable. If only a function table exists, wrap specific known methods, as AtomLazers does:

function Addon.Connect(api, emit)
    local original = api.SetEnabled
    local wrapper = function(self, value)
        assert(type(value) == "boolean", "Expected boolean")
        original(self, value)
        emit("SetEnabled", value)
    end
    api.SetEnabled = wrapper

    return {{Disconnect = function()
        if api.SetEnabled == wrapper then
            api.SetEnabled = original
        end
    end}}
end

This replaces the tutorial's Connect; do not define it twice. It assumes this teaching system's colon method and no return values. Preserve the actual API's calling convention and return values when adapting it. Call the original first, then emit: failed actions should not be recorded.

A function reference cached before wrapping bypasses the wrapper. Client APIs use a separate context; a server addon does not automatically capture client actions. Such systems need a trusted server API/signal. Do not wrap unrelated methods or every method indiscriminately.

State versus one-shot effects

ReplayOnSeek=true often suits enabled state, color and position: HOTLINE restores these by replaying state commands. Reset should establish a meaningful baseline.

Keep ReplayOnSeek=false for a Fire command, confetti burst or one-shot pulse. Manual seeking skips it. Normal timed playback executes it; starting from zero executes commands at zero. This does not prevent repeated effects on a new show run. If repetition is invalid for your game's logic, enforce conditions in the actual API.

Resolve/Connect register the integration, not perform a show. Never activate effects there. A snapshot must not itself activate a one-shot effect.

Reliability and release checks

Addon registration has a 10-second timeout. Avoid infinite WaitForChild in Resolve/Connect. Return nil for a missing dependency and restart after installing it. HOTLINE readiness and addon readiness are separate.

Keep Validate, Run, Reset and signal handlers short and non-yielding. Shared event limits, queue limits and command budgets apply. HOTLINE suppresses recording feedback during its dispatch/reset; do not delay an emit with task.delay from a playback command, because that echo escapes the suppression window.

  1. Verify direct system control without HOTLINE.
  2. Check GetAddons reports ready and Output has no errors.
  3. Record Timed and Capture; inspect offsets and arguments in Events.
  4. Save, load and replay. Playback must not increase the recorded event count.
  5. Test Stop, seeking, restarting and Snapshot if implemented.
  6. Test missing dependencies, invalid arguments and incompatible APIs.
  7. Test a real multiplayer session: a mocked harness cannot verify replication or fixture physics.

Addons execute trusted server code. Do not load them from arbitrary client input or expose a generic RemoteEvent that can execute any command.
